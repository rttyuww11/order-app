# COZY 커피 주문 앱 — 프런트엔드 PRD

## 1. 개요

### 1.1 목적
주문하기 및 관리자 화면의 UI와 사용자 동작 요구사항을 정의한다. 각 화면의 첨부 와이어프레임을 기준으로 한다.

### 1.2 목표
고객이 커피 메뉴와 옵션을 선택해 주문을 접수하고, 관리자가 주문 현황을 확인·처리하며 메뉴 재고를 조정할 수 있게 한다.

### 1.3 범위
- 포함: 주문하기 화면의 메뉴 목록, 메뉴 옵션 선택, 장바구니 및 주문 접수
- 포함: 관리자 화면의 주문 요약, 메뉴 재고 조정, 주문 현황 및 주문 상태 변경
- 제외: 사용자 인증, 결제
- 주문 접수는 결제 없이 주문을 등록하는 것으로 한다.

## 2. 사용자 및 주요 시나리오

**사용자:** 커피를 주문하려는 고객

**시나리오:** 사용자는 메뉴와 가격을 확인하고 원하는 추가 옵션을 선택한 뒤 `담기`를 누른다. 장바구니에서 구성과 총 금액을 확인하고 `주문하기`를 눌러 주문을 접수한다.

## 3. 화면 구성

### 3.1 상단 내비게이션
- 왼쪽에 `COZY` 브랜드명을 표시한다.
- 오른쪽에 `주문하기`, `관리자` 메뉴를 제공한다.
- 현재 화면인 `주문하기` 메뉴는 활성 상태로 구분한다.
- `관리자` 메뉴는 관리자 화면으로 이동한다.

### 3.2 메뉴 카드 목록
- 주문 가능한 커피를 카드 형태로 표시한다.
- 각 카드에는 메뉴 이미지, 메뉴명, 기본 가격, 간단한 설명, 선택 옵션, `담기` 버튼이 포함된다.
- 와이어프레임의 메뉴 및 가격 예시는 다음과 같다.

| 메뉴 | 기본 가격 |
|---|---:|
| 아메리카노(ICE) | 4,000원 |
| 아메리카노(HOT) | 4,000원 |
| 카페라떼 | 5,000원 |

- 메뉴 정보는 실제 데이터에 따라 표시한다. 이미지가 없을 때에도 카드 레이아웃이 유지되어야 한다.

### 3.3 옵션
- 옵션은 체크박스로 표시하고, 사용자가 선택하거나 해제할 수 있다.
- 와이어프레임의 옵션 예시는 `샷 추가 (+500원)`, `시럽 추가 (+0원)`이다.
- 선택한 옵션은 해당 메뉴의 가격 및 장바구니 항목에 반영한다.
- 카드마다 사용할 수 있는 옵션이 다를 수 있으며, 메뉴 데이터에 정의된 옵션을 표시한다.

### 3.4 장바구니
- 메뉴 카드 아래에 장바구니 영역을 표시한다.
- 각 항목에 메뉴명, 선택 옵션, 수량, 항목 금액을 표시한다.
- 장바구니 합계를 `총 금액`으로 표시한다.
- 동일한 메뉴와 옵션 조합을 다시 담으면 수량을 합산한다. 서로 다른 옵션 조합은 별도 항목으로 표시한다.
- 장바구니가 비어 있을 때는 비어 있음을 안내하고 주문 버튼을 비활성화한다.
- 와이어프레임에 없는 수량 변경·항목 삭제 컨트롤은 이번 범위의 필수 기능에 포함하지 않는다.

## 4. 기능 요구사항

### FR-01 메뉴 표시
- 화면 진입 시 주문 가능한 메뉴를 불러와 카드 목록으로 표시한다.
- 메뉴 로딩 중, 메뉴가 없는 경우, 조회에 실패한 경우를 각각 구분해 사용자에게 알린다.
- 조회 실패 시 오류 안내와 재시도 방법을 제공한다.

### FR-02 옵션 선택 및 담기
- 사용자는 메뉴를 담기 전에 원하는 옵션을 선택할 수 있다.
- `담기`를 누르면 해당 메뉴와 선택 옵션을 장바구니에 추가한다.
- 항목 단가는 `기본 가격 + 선택 옵션 가격`으로 계산한다.
- 예: 기본 가격 4,000원에 500원 샷 추가를 선택하면 한 잔 가격은 4,500원이다.
- 추가 후 장바구니 항목과 합계가 즉시 갱신되어야 한다.

### FR-03 장바구니 금액 표시
- 항목 금액은 `항목 단가 × 수량`으로 계산한다.
- 총 금액은 모든 항목 금액을 더해 계산한다.
- 금액은 천 단위 구분 기호와 `원`을 사용해 표시한다.
- 와이어프레임 예시처럼 아메리카노(ICE) 1잔(샷 추가 포함, 4,500원)과 아메리카노(HOT) 2잔(각 4,000원)의 총 금액은 12,500원이다.

### FR-04 주문 접수
- 장바구니에 항목이 있을 때만 주문 버튼을 활성화한다.
- `주문하기`를 누르면 현재 장바구니 항목, 수량, 선택 옵션을 포함해 주문 접수를 요청한다.
- 요청 중에는 진행 상태를 표시하고 중복 제출을 막는다.
- 접수 성공 시 성공 안내를 표시하고 장바구니를 비운다.
- 접수 실패 시 오류를 알리고 장바구니를 유지해 재시도할 수 있게 한다.
- 결제는 진행하지 않는다.

## 5. UI 및 접근성 요구사항

- 와이어프레임의 기본 배치 순서인 헤더, 메뉴 카드 목록, 장바구니를 따른다.
- 메뉴 카드의 정보와 버튼 배치를 일관되게 유지한다.
- 다양한 화면 폭에서 메뉴와 장바구니를 사용할 수 있도록 반응형으로 구성한다.
- 내비게이션, 체크박스, 버튼은 키보드로 조작할 수 있어야 한다.
- 선택 상태와 포커스 상태를 알아볼 수 있게 표시한다. 가격 및 옵션 정보는 색상만으로 전달하지 않는다.

## 6. 상태 및 예외 처리

| 상태 | 기대 동작 |
|---|---|
| 메뉴 로딩 중 | 로딩 상태 표시 |
| 메뉴 목록이 비어 있음 | 주문 가능한 메뉴가 없음을 안내 |
| 메뉴 조회 실패 | 오류 안내 및 재시도 제공 |
| 장바구니가 비어 있음 | 빈 상태 안내 및 주문 버튼 비활성화 |
| 메뉴 담기 성공 | 항목, 수량, 금액 갱신 |
| 주문 접수 중 | 진행 상태 표시 및 중복 요청 방지 |
| 주문 접수 성공 | 성공 안내 및 장바구니 초기화 |
| 주문 접수 실패 | 오류 안내 및 장바구니 유지 |

## 7. 수용 기준

1. 메뉴 카드에서 메뉴명, 기본 가격, 설명과 사용 가능한 옵션을 확인할 수 있다.
2. 옵션을 선택하고 담으면 옵션 이름과 추가 금액이 장바구니에 반영된다.
3. 같은 메뉴·옵션 조합을 다시 담았을 때 수량과 금액이 정확히 합산된다.
4. 각 항목 금액과 총 금액이 올바르게 계산되어 표시된다.
5. 장바구니가 비어 있으면 주문을 접수할 수 없다.
6. 주문 요청 중 중복 접수가 방지된다.
7. 주문 성공 시 안내가 표시되고 장바구니가 비워지며, 실패 시 장바구니가 보존된다.
8. 메뉴 로딩·빈 결과·조회 오류가 서로 구분되어 안내된다.

## 8. 미결정 사항

- 장바구니의 수량 변경 및 항목 삭제 기능은 와이어프레임에서 확인되지 않아 필수 범위에서 제외했다. 필요한 경우 구현 전에 정책을 결정한다.
- 주문 접수 후 주문 번호나 주문 요약을 보여주는 별도 완료 화면은 이번 와이어프레임에 정의되어 있지 않다.

## 9. 관리자 화면

### 9.1 사용자 및 목표

**사용자:** 매장의 주문과 메뉴 재고를 관리하는 운영자

관리자는 주문 건수 및 주문 상태별 현황을 파악하고, 메뉴별 재고를 조정하며, 주문을 확인하고 상태를 순차적으로 변경한다.

### 9.2 화면 구성

#### 상단 내비게이션
- 주문하기 화면과 동일한 `COZY` 브랜드 및 `주문하기`, `관리자` 메뉴를 표시한다.
- 현재 화면인 `관리자` 메뉴를 활성 상태로 구분한다.

#### 관리자 대시보드
- 주문 통계 영역에 총 주문 수와 상태별 주문 수를 표시한다.
- 와이어프레임의 상태별 분류는 `주문 접수`, `제조 중`, `제조 완료`다.
- 각 수치는 현재 시스템 주문 데이터를 반영한다. 와이어프레임의 숫자는 예시 데이터이며 고정값이 아니다.

#### 재고 현황
- 관리 대상 메뉴마다 메뉴명, 현재 재고 수량, `+`, `-` 버튼을 표시한다.
- 와이어프레임의 메뉴 예시는 아메리카노(ICE), 아메리카노(HOT), 카페라떼이며 각 10개는 예시 수량이다.
- 재고는 정수 수량으로 표시한다.

#### 주문 현황
- 주문별 접수 일시, 주문 메뉴 및 수량, 주문 금액을 표시한다.
- 주문에 여러 메뉴가 포함된 경우 모든 주문 항목을 해당 주문 안에서 확인할 수 있어야 한다.
- 주문마다 현재 상태를 표시하고, 상태를 다음 단계로 변경하는 조작을 제공한다.
- 주문이 없을 때는 주문이 없음을 안내한다.

### 9.3 기능 요구사항

#### FR-05 주문 현황 요약
- 관리자 화면 진입 시 주문 데이터와 통계를 조회해 대시보드에 표시한다.
- 총 주문 수와 주문 상태별 건수는 주문 목록과 일치해야 한다.
- 통계 조회 중에는 로딩 상태를 표시하고, 조회 실패 시 오류 안내와 재시도 방법을 제공한다.

#### FR-06 재고 조정
- `+` 버튼을 누르면 해당 메뉴의 재고를 1개 증가시킨다.
- `-` 버튼을 누르면 해당 메뉴의 재고를 1개 감소시킨다.
- 재고는 0 미만이 될 수 없으며, 0개일 때 `-` 조작은 재고를 음수로 만들지 않는다.
- 변경 결과를 화면에 반영하고 서버에 저장한다.
- 저장 중에는 중복 입력으로 재고가 여러 번 잘못 변경되지 않도록 처리하고, 저장 실패 시 실패 사실을 알린다.

#### FR-07 주문 상태 변경
- 주문 현황에서 주문의 상세 항목과 금액을 확인할 수 있다.
- 새 주문의 기본 상태는 `주문 접수`다. 관리자가 해당 상태를 누르면 `제조 중`, 다시 누르면 `제조 완료`로 순차 변경하도록 서버에 요청한다.
- 상태 변경은 `주문 접수` → `제조 중` → `제조 완료` 순서만 허용하며, 이전 단계로 되돌리거나 단계를 건너뛸 수 없다.
- 처리 중에는 버튼을 비활성화하거나 진행 상태를 표시해 중복 처리를 막는다.
- 처리 성공 시 해당 주문과 대시보드 통계를 갱신한다. `제조 완료` 이후에는 상태 변경 조작을 제공하지 않는다.
- 처리 실패 시 오류 안내를 표시하고 서버에 저장된 기존 상태를 유지한다.

### 9.4 주요 상태 및 예외 처리

| 상황 | 기대 동작 |
|---|---|
| 대시보드 데이터 로딩 중 | 요약, 재고, 주문 목록의 로딩 상태 표시 |
| 조회 결과가 비어 있음 | 재고 또는 주문이 없음을 각 영역에서 안내 |
| 데이터 조회 실패 | 오류 안내 및 재시도 제공 |
| 재고 변경 저장 중 | 진행 상태 표시 및 중복 변경 방지 |
| 재고 변경 실패 | 오류 안내, 저장된 재고와 미저장 변경을 구분 |
| 주문 상태 변경 중 | 진행 상태 표시 및 중복 처리 방지 |
| 주문 상태 변경 성공 | 주문 목록 및 상태별 통계 갱신 |
| 주문 상태 변경 실패 | 오류 안내 및 서버에 저장된 기존 상태 유지 |

### 9.5 관리자 화면 수용 기준

1. 관리자 화면에서 총 주문 수와 주문 접수·제조 중·제조 완료 건수를 확인할 수 있다.
2. 메뉴별 현재 재고 수량과 재고 조정 버튼을 확인할 수 있다.
3. `+`, `-` 조작은 한 번에 1개씩 재고를 변경하며, 재고가 음수가 되지 않는다.
4. 재고 변경 결과가 저장 성공 후 화면에 반영되고, 실패 시 오류가 안내된다.
5. 주문 목록에서 접수 일시, 주문 항목과 수량, 주문 금액을 확인할 수 있다.
6. 주문 상태를 `주문 접수`에서 `제조 중`, `제조 중`에서 `제조 완료`로 순차 변경하면 성공 결과와 최신 요약 수치가 표시된다.
7. 주문 또는 재고 변경 요청 실패 시 성공한 것처럼 표시하지 않는다.

### 9.6 미결정 사항

- 재고 변경 단위는 와이어프레임에서 명시되지 않아 버튼 한 번당 1개로 해석했다. 다른 단위가 필요하면 구현 전에 확정한다.
- 주문 목록의 정렬 순서, 페이지네이션, 자동 새로고침 여부는 와이어프레임에 정의되어 있지 않다.

## 10. 백엔드 PRD

### 10.1 목적 및 범위

프런트엔드에서 사용하는 메뉴, 옵션, 재고, 주문 데이터를 데이터베이스에 영속화하고 API로 제공한다. 메뉴 조회, 주문 생성과 재고 차감, 주문 단건 조회 및 관리자 화면의 주문·재고 관리가 범위에 포함된다. 결제와 사용자 인증은 현재 범위에서 제외한다.

### 10.2 데이터 모델

모든 금액은 원 단위의 정수로 저장한다. 기본 식별자는 데이터베이스에서 생성하는 고유 ID를 사용한다.

#### Menus

| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | ID | 예 | 메뉴 식별자 |
| name | 문자열 | 예 | 커피 메뉴 이름 |
| description | 문자열 | 아니요 | 메뉴 설명 |
| price | 정수 | 예 | 기본 가격(원), 0 이상 |
| image_url | 문자열 | 아니요 | 메뉴 이미지 URL |
| stock_quantity | 정수 | 예 | 현재 재고 수량, 0 이상 |
| is_available | 불리언 | 예 | 주문 가능 여부 |

메뉴 목록 API는 주문 가능한 메뉴를 반환한다. 재고 수량은 고객용 메뉴 응답에도 포함할 수 있으며, 관리자 화면은 메뉴 관리 응답의 재고 수량을 표시한다. 재고가 0인 메뉴는 주문할 수 없다.

#### Options

| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | ID | 예 | 옵션 식별자 |
| menu_id | ID | 예 | 연결된 메뉴 ID |
| name | 문자열 | 예 | 옵션 이름 |
| price | 정수 | 예 | 추가 가격(원), 0 이상 |

각 옵션은 하나의 메뉴에 연결된다. 메뉴 조회 시 해당 메뉴에 선택 가능한 옵션을 함께 제공한다. 예: `샷 추가`는 500원, `시럽 추가`는 0원.

#### Orders

| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | ID | 예 | 주문 식별자 |
| ordered_at | 일시 | 예 | 서버가 기록하는 주문 접수 일시 |
| status | 열거형 | 예 | `RECEIVED`, `PREPARING`, `COMPLETED` 중 하나 |
| total_amount | 정수 | 예 | 주문 총액(원) |

#### OrderItems

| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| id | ID | 예 | 주문 항목 식별자 |
| order_id | ID | 예 | 연결된 주문 ID |
| menu_id | ID | 예 | 주문 당시 메뉴 식별자 |
| menu_name | 문자열 | 예 | 주문 당시 메뉴명 스냅샷 |
| quantity | 정수 | 예 | 주문 수량, 1 이상 |
| unit_price | 정수 | 예 | 주문 당시 메뉴 기본 가격(원) |
| item_amount | 정수 | 예 | 옵션 포함 항목 단가 × 수량(원) |

#### OrderItemOptions

| 필드 | 형식 | 필수 | 설명 |
|---|---|---:|---|
| order_item_id | ID | 예 | 연결된 주문 항목 ID |
| option_id | ID | 예 | 선택된 옵션 ID |
| option_name | 문자열 | 예 | 주문 당시 옵션명 스냅샷 |
| option_price | 정수 | 예 | 주문 당시 옵션 추가 가격(원) |

주문 항목과 옵션의 이름 및 가격은 주문 시점의 값으로 저장해, 이후 메뉴나 옵션이 변경되어도 기존 주문 내역과 금액이 바뀌지 않도록 한다. 항목 금액은 `(unit_price + 선택 옵션 가격 합계) × quantity`로 계산하고, 주문 총액은 모든 항목 금액의 합으로 계산한다. 서버가 가격과 합계를 계산하며 클라이언트가 보낸 금액은 신뢰하지 않는다.

### 10.3 데이터 흐름 및 사용자 흐름

1. 고객이 `주문하기` 화면을 열면 클라이언트가 API에서 주문 가능한 메뉴와 각 메뉴의 옵션을 조회해 표시한다. 관리자 화면에서는 메뉴의 재고 수량도 표시한다.
2. 고객이 메뉴, 수량 및 옵션을 선택해 장바구니에 담는다. 장바구니는 화면에서 선택한 주문 초안이며, 아직 서버에 주문으로 저장되지 않는다.
3. 고객이 장바구니의 `주문하기`를 누르면 메뉴 ID, 수량, 옵션 ID를 서버에 전송한다. 서버는 메뉴 및 옵션의 유효성, 주문 가능 여부와 재고를 확인하고, 서버 기준 가격으로 금액을 계산한다.
4. 서버는 주문과 주문 항목 및 옵션 스냅샷을 저장하고, 같은 데이터베이스 트랜잭션 안에서 주문 수량만큼 메뉴 재고를 차감한다. 저장 또는 재고 차감 중 하나라도 실패하면 전체 작업을 롤백해 주문만 저장되거나 재고만 차감되는 상황을 방지한다.
5. 주문 생성 시 기본 상태는 `RECEIVED`(화면 표시명 `주문 접수`)다. 관리자 화면의 주문 현황은 저장된 주문, 항목, 옵션, 접수 일시와 금액을 조회해 표시한다.
6. 관리자가 주문의 상태 변경 동작을 실행하면 상태는 `RECEIVED` → `PREPARING` → `COMPLETED` 순서로만 변경된다. 화면 표시명은 각각 `주문 접수` → `제조 중` → `제조 완료`로 한다. 완료 상태에서 추가 전이는 허용하지 않는다.
7. 주문 생성 성공 응답으로 받은 주문 ID를 사용해 해당 주문의 상세 정보를 다시 조회할 수 있다.

### 10.4 API 설계

JSON 요청 및 응답을 사용한다. 모든 오류 응답은 `{ "error": { "code": "문자열", "message": "문자열" } }` 형태로 반환한다.

| 기능 | 메서드 및 경로 | 요청 | 성공 응답 |
|---|---|---|---|
| 주문 가능 메뉴 및 옵션 조회 | `GET /api/menus` | 없음 | `200`: 메뉴 목록. 각 메뉴에 `id`, `name`, `description`, `price`, `imageUrl`, `stockQuantity`, `options` 포함 |
| 관리자 메뉴 및 재고 조회 | `GET /api/admin/menus` | 없음 | `200`: 전체 관리 메뉴와 재고 수량 |
| 재고 변경 | `PATCH /api/admin/menus/{menuId}/stock` | `{ "delta": 1 }` 또는 `{ "delta": -1 }` | `200`: 변경된 메뉴 및 `stockQuantity` |
| 주문 생성 | `POST /api/orders` | `{ "items": [{ "menuId": "id", "quantity": 1, "optionIds": ["id"] }] }` | `201`: 생성된 주문 ID, 접수 일시, 상태, 주문 항목 및 금액 |
| 주문 단건 조회 | `GET /api/orders/{orderId}` | 없음 | `200`: 주문 및 모든 항목, 선택 옵션, 금액, 상태 |
| 관리자 주문 현황 조회 | `GET /api/admin/orders` | 없음 | `200`: 주문 목록(항목 포함)과 총 주문 수 및 상태별 건수 |
| 주문 상태 변경 | `PATCH /api/admin/orders/{orderId}/status` | `{ "status": "PREPARING" }` 또는 `{ "status": "COMPLETED" }` | `200`: 변경된 주문 상태 |

#### API 검증 및 실패 동작

- 주문 생성 요청은 항목이 하나 이상이어야 하며, 수량은 1 이상의 정수여야 한다. 옵션은 해당 메뉴에 연결된 유효한 옵션이어야 한다.
- 주문에 포함된 모든 메뉴의 재고를 확인하고 차감하는 과정은 원자적으로 수행한다. 동시 주문으로 재고가 부족해지면 주문을 생성하지 않고 `409 Conflict`를 반환한다.
- 존재하지 않는 메뉴·옵션·주문은 `404 Not Found`, 잘못된 입력 또는 허용되지 않는 상태 전이는 `400 Bad Request`, 서버 오류는 `500 Internal Server Error`로 반환한다.
- 재고 변경은 정수 `delta`의 `+1` 또는 `-1`만 허용하고, 결과 재고가 0 미만이면 변경하지 않는다.
- 주문 상태 변경은 현재 상태의 바로 다음 단계만 허용한다. 이미 처리된 상태 변경 요청은 유효하지 않은 전이로 처리하며, 서버 상태를 임의로 건너뛰지 않는다.
- 메뉴, 주문 및 재고의 조회·저장 실패는 오류 응답으로 명시한다. 클라이언트는 실패한 주문을 성공으로 표시하거나 장바구니를 비우지 않는다.

### 10.5 백엔드 수용 기준

1. 메뉴 조회 응답에 메뉴 정보와 메뉴별 옵션이 포함되고, 관리자 조회에서 각 메뉴의 현재 재고를 확인할 수 있다.
2. 유효한 주문 요청은 서버에서 가격을 다시 계산해 주문·항목·옵션과 주문 시점의 가격 정보를 저장한다.
3. 주문 생성 성공 시 기본 상태가 `RECEIVED`이고, 서버가 기록한 접수 일시와 주문 ID를 반환한다.
4. 주문 저장과 재고 차감은 원자적이며, 재고 부족 또는 저장 실패 시 주문과 재고가 부분 반영되지 않는다.
5. 주문 ID로 주문 정보, 주문 항목, 선택 옵션, 상태와 금액을 조회할 수 있다.
6. 관리자 주문 목록과 상태별 건수가 저장된 주문 데이터와 일치한다.
7. 주문 상태는 `RECEIVED` → `PREPARING` → `COMPLETED` 순서로만 전이하고, 관리 화면에 해당 상태명이 일관되게 표시된다.
8. 재고는 음수가 되지 않으며 입력 검증, 미존재 데이터, 재고 부족 및 상태 전이 오류가 명시적인 오류 응답으로 반환된다.

### 10.6 백엔드 미결정 사항

- 데이터베이스 제품, 배포 환경, API 인증 및 관리자 권한 부여 방식은 현재 PRD에서 정하지 않았다. 인증이 제외된 범위에서는 관리자 API를 공개 네트워크에 운영 배포하기 전에 접근 통제 방식을 별도로 결정해야 한다.
- 주문 목록의 정렬·페이지네이션과 실시간 갱신 방식은 기존 관리자 화면 요구사항에 따라 별도 결정한다.
